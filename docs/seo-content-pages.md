# SEO content pages: one page per thing the app holds

How we turn an app's catalogue into search landing pages that send people to
the App Store, and the rules that keep thousands of generated pages from
hurting the site. Built and measured on DailyBook (October 2026: 16,174 book
pages on `chargingpixels.com/apps/dailybook/`, ~$100 of model time for all of
them). Reference implementation: `daily-book/scripts/web/` (runbook in its
README, reasoning in `docs/decisions/website-seo.md`).

## The shape

- **A static site in the company site repo**, generated by a script in the
  app repo, deployed by pushing the site repo's `main` (Cloudflare Workers
  static assets). No server, no CMS.
- **One page per item people search for** (a book, a recipe, a film), plus
  hub pages that link them: lists, author/creator pages, a browsable
  directory by subject, and the landing page.
- **Every page does three jobs:** answer the search (what is it, how long,
  who made it, the famous parts), give a real taste (DailyBook shows the
  whole first chapter and plays it read aloud), and offer the app with an
  App Store link carrying a per-page campaign token (`?ct=web-<slug>`, 40
  characters at most) so installs can be attributed in App Store Connect.

## Rules that turned out to matter

**Build from the app's own code.** The generator loads the app's TypeScript
(chapter detection, text cleaning) through a transpile-on-load hook instead
of re-implementing it, so the web can never disagree with the app. A regex
re-implementation put late chapters one off in the first week.

**The page promises only what it holds.** "Read X free online" ranked for a
query the page did not satisfy (it had chapter 1 and an install button).
Title and H1 are `{Short title} by {Creator}`, the site name only if the tag
still fits ~60 characters, and the lede says what is here and what is in the
app, naming the platform ("for iPhone"). Take short titles from the source's
own record when it has them: our catalogue had flattened title and subtitle,
which gave 3,597 pages 100-character titles and let two editions of one book
pass the duplicate check.

**Model-written copy is never trusted, it is checked.** Nobody reviews
10,000 pages, so every claim a script can test is tested: a quote ships only
if found word for word in the text (half of all proposed "famous lines"
fail, one was from a film); a character only if the text names them three
times; a blurb only if it passes the house voice (banned words, length, no
em dashes) with one retry, then nothing. Data that cannot be checked (a
publication year) comes from a real source or not at all: the catalogue's
"year" was the digitisation date, and 10,000 pages said Shakespeare wrote in
1998 before anyone noticed.

**Index only what can carry weight.** A page per item at scale with ~40
words of unique text over freely available source text is what Google's
scaled-content policy describes, and a site-wide demotion takes the good
pages with it. So every page is built for readers, but only some ask to be
indexed: well-known items, popular ones (a downloads threshold, never a rank,
because every batch numbers its ranks from 1), or ones with verified extras.
The rest carry `noindex,follow`. The sitemaps list only indexed pages, split
by type under an index (Search Console then reports per type), with
`lastmod` from the content's date, never the build's.

**Facts beat adjectives.** Unique text that costs nothing: creator and dates,
length and reading time, subjects as links, how many people use the source
each month, an audiobook if one exists, and a short block of questions
answered from that data ("How long is X?", "Is X free?", "How does X
begin?"). Plain HTML, no FAQ schema (Google stopped showing it for most
sites).

**Every page links out.** A page that links to nothing is a dead end for
crawlers: "More like this" (same creator, the subject's best-known items, and
neighbours in popularity, so the long tail links to itself), subject chips,
and every page number of a directory linked, not a window of three.

**One page per work, and one place per thing.** An audiobook is a section of
its book's page (title "X by Y, book and audiobook" when it fits, a question,
`workExample` in the schema), never a page of its own competing with it.
Two editions of one work get one page.

**Live within the hosting limit on purpose.** Workers static assets allow
20,000 files a deploy on the free plan (100,000 paid). The build enforces a
budget (19,000), keeps the best pages and fills the rest in priority order,
and fails rather than publish over it. Spending files well beat paying for
more: dropping 3,516 one-item creator pages (all `noindex`, near copies of
one tile) paid for 6,500 more items.

**Media plays from where it lives.** Public-domain audio streams from the
Internet Archive into a plain `<audio preload="none">`: no bytes before play,
no files of ours. Only play a clip proven to match what the page shows (the
recording's first real section, one chapter, the page's kind, a plausible
length); the wrong audio under "Listen to chapter 1" is worse than none.

**Audit the whole build, not a sample.** A read-only script over every
generated file catches what spot checks miss: broken internal links (removing
a page type leaves links to it), duplicate titles and descriptions, invalid
JSON-LD, `noindex` pages listed in a sitemap or indexable ones missing from
it, one H1 per page. Then check the host: `http://` must redirect to
`https://` (Cloudflare: SSL/TLS, Edge Certificates, "Always Use HTTPS"; it
is off by default) and `www` to the bare domain.

## Batches of generated copy

- **Run the model stripped:** `claude -p` with its own system prompt, no
  tools, no MCP, no settings, thinking and prompt caching off, ten items a
  call, JSON validated locally. About $0.007 an item, where a default call
  costs $0.115 in overhead alone. Structured-output mode plus thinking cost
  8x for nothing.
- **Resumable everything:** state per item, a failed call costs no attempt,
  a usage-limit message pauses and retries later. Fetch sources politely (a
  sanctioned mirror, two seconds apart per host; one host per worker doubled
  throughput without any host seeing more).
- **Run overnight detached:** `nohup perl -MPOSIX -e 'POSIX::setsid(); exec
  @ARGV' caffeinate -i node overnight.cjs ...`. Without its own session, a
  restart of the agent that started it kills the run.
- **Publish carefully:** pull with rebase before pushing (someone merges at
  night), ask git whether anything is staged with `git diff --cached --quiet`
  (listing 21,000 staged paths overflowed the buffer and crashed the
  publish), and never publish a build that failed.
- **A richer second pass for the items that matter** (the best-known few
  hundred) merges into what they have and never removes anything.

## Measurement and consent

- **Search Console** (a Domain property, DNS TXT record) and **Bing
  Webmaster Tools** (import from Search Console; its auth file at the site
  root). Submit the sitemap index by its full URL. The number to watch is
  "Crawled, currently not indexed" on pages you meant to index: that is the
  thin-content verdict, and it decides whether to tighten the index rule
  before generating more.
- **Cloudflare Web Analytics** for everyone: cookieless, no banner. Its
  automatic injection does not reach pages served by Workers, so the build
  writes the snippet.
- **Google Analytics only behind consent** (EU ePrivacy): nothing from
  Google loads before Accept; Decline is remembered and clears `_ga`
  cookies; a "Cookie settings" link in every footer reopens the choice. The
  banner copy can stay general ("a few cookies to see how these pages are
  read"); the privacy page names the tools and describes the website
  separately from the app.
- **Installs per page** come from the App Store campaign tokens, which is the
  number the whole thing exists for.

## What it does not do

Pages are not read online in full (that would need a page per chapter and a
Worker), and generated volume is not the goal: wait for indexing data before
adding more pages.
